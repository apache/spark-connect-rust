# PySpark 4.3.0 module audit (the `pyspark-client` packages)

The class diff (`4.3.0-introspection-diff.md`) covers the connect classes. This audit covers
the modules and module-level names of the `pyspark-client` package: every module of the
packages of `connect_packages` (`python/packaging/client/setup.py` at `v4.3.0`), 352 modules.

Method: import each module from the v4.3.0 source with `pyspark.core` and `py4j` blocked (they
are not in `pyspark-client`, so `is_remote_only()` holds), and from this client. Then diff the
public names that the official module defines itself (functions and classes whose
`__module__` is the module), its submodules and its constants. Imported names (typing
aliases, re-exported helpers) are left out. 27 modules do not import in `pyspark-client`
either (`pyspark.mllib.*`, `pyspark.java_gateway`, `pyspark.shell`), and are left out.

## Vendored modules

These modules of `pyspark-client` are Apache Spark's own, vendored from v4.3.0 as they are at the
same paths under `python/pyspark` (`scripts/check_vendored_upstream.sh` keeps them byte-identical
to the tag). They import as in `pyspark-client`:

- PySpark's RDD helpers: `pyspark.join`, `rddsampler`, `resultiterable`, `shuffle`, `statcounter`;
- its tools: `pyspark.errors_doc_gen`, `pyspark.install`, `pyspark.threaddump`, and
  `pyspark.sql.transpile` and `pyspark.sql.connect.local_server`, which the classic
  `UserDefinedFunction` and the builder of the classic `SparkSession` use;
- the modules that the server runs in Python: `pyspark.worker` and `pyspark.daemon`, PySpark's
  Python worker and its daemon, `pyspark.worker_message`,
  `pyspark.sql.streaming.python_streaming_source_runner`, `pyspark.sql.connect.streaming.worker`
  (`foreach_batch_worker`, `listener_worker`), and `pyspark.sql.streaming.proto`, whose
  `StateMessage_pb2`, which protoc generates, needs `protobuf`;
- the modules of PySpark's gRPC client: `pyspark.sql.connect.client.artifact`, `reattach` and
  `retries`, and `pyspark.sql.connect.proto.base_pb2_grpc`. They import grpcio (`reattach` and
  `retries` also grpcio-status and googleapis-common-protos), which `pyspark-client` requires and
  this client does not, so they import where those are installed. `base_pb2_grpc` builds its
  stub and servicer on the messages of the Rust protobuf runtime. The Rust transport does not use
  these modules. `pyspark.sql.connect.client` binds them as its attributes when they are
  imported, where PySpark's has them from its own import, as its `core` imports them.

`pyspark-client` 4.3.0 requires Python 3.11. `pyspark.worker_message` (`typing.TypeAlias`) and
`pyspark.sql.transpile` (`match` statements) need Python 3.10, and so do `pyspark.worker` and the
two streaming workers, which import `pyspark.worker_message`. So on Python 3.9, which this client
supports, they do not import.

## Not gaps

- **Server-side names**, which run on the server's Python worker (official PySpark there):
  `stateful_processor_api_client.SCALAR_TYPES`
- **RDD and classic internals**, of which a Connect client has no use:
  - the RDD-based `pyspark.mllib`, most of which does not import in `pyspark-client` either
  - the py4j converters of `pyspark.sql.types` (`DateConverter`, `DatetimeConverter`, `DatetimeNTZConverter`, `DayTimeIntervalTypeConverter`, `NumpyArrayConverter`, `NumpyScalarConverter`, `TimeConverter`)
  - the classic dispatch helpers of `pyspark.sql.utils` (`dispatch_*_method`, `try_remote_*`, `to_java_array`, `to_scala_map`, `get_active_spark_context`, `ForeachBatchFunction`)
  - `pyspark.sql.group.dfapi` and `df_varargs_api`, `PandasGroupedOpsMixin`, `OptionUtils`, `JStreamingQueryListener`
  - `StreamingCheckpointManager`, which PySpark documents as supported in Spark Classic only
- **The gRPC client**, which the Rust transport replaces:
  - `pyspark.sql.connect.client.core`
  - `convert_exception` and `convert_observation_errors` of `pyspark.errors.exceptions.connect`
  - the plan and expression classes of `pyspark.sql.connect.plan` and `pyspark.sql.connect.expressions`, which the Rust core builds (except those that SPARK-61111 and SPARK-61116 port), and `WindowFrame`, `StreamingQueryListenerBus`
- **Types of the Rust core**: `DataTypeSingleton`, the metaclass of the singleton types of PySpark.
- **`pyspark.ml.connect`**: exposes the native ML API of the Rust core (see `docs/compatibility.md`). Native fits return the shared `MLModel`. Vendored helper classes, including `ArrayAssembler` and the deprecated scaler model classes, remain available from their existing modules.
- **Submodule attributes** that differ only because of import order (`pyspark.find_spark_home`, `pyspark.sql.conversion`, `pyspark.sql.streaming.state`, ...). The modules import.

### Native feature execution

All 38 standard `pyspark.ml.feature` stages now have native Rust and Python fit/transform
execution, constructors and named setters. See `docs/compatibility.md` for the inventory,
scaler migration and model-method limits. This does not mark the vendored ML package or
specialized model methods as fully native. `pyspark.ml.connect.feature` retains its vendored
source; the package initializer installs the native classes onto that module.


## Native standard ML statistics

`pyspark.ml.stat` now exports the native `ChiSquareTest`, `Correlation`,
`KolmogorovSmirnovTest`, `Summarizer` and `SummaryBuilder` classes, and PySpark's plain
`MultivariateGaussian` holder. It is a Rust-backed shim and is therefore excluded from the
vendored-file inventory, but included in linting. Signature, protocol and numerical fixtures use
standard `pyspark.ml.stat` from official PySpark 4.3.0 as the reference.

Deprecated public `pyspark.ml.connect` APIs are outside the scope of future ML
feature and parity work. Internal protocol helpers used by standard `pyspark.ml`
remain available where existing implementations need them.
